# 3.6.10 portal audit

The release fixes inconsistent order accounting across the administration and agent portals. Requests are charged when completed. Reversals remain distinct from cash receipts, and reports include noncash adjustments without offsetting one customer's debt against another customer's credit.

## Changes

- Atomic staff order price edits and agent credit/cash refunds, with stale-data checks and rollback on failure.
- Exact order and customer links in statements; movement numbers, running balances and English date/time digits.
- Preserved invoice price snapshots and discounts during agent edits. Manual orders insert their final prices and discounts once. Repeated submit clicks are guarded.
- Agent RLS restrictions prevent direct balance changes, fabricated payments and unauthorized notification broadcasts. Agent request identity and edit permissions are normalized by the database.
- Account restoration refreshes profile state; suspended or archived profiles cannot restore access. Logout clears notification state. Wrong-portal sign-ins are signed out.
- Profile and notification persistence failures propagate to the interface. Settings are published locally only after the server confirms the save.
- Complete paginated data loads retain the previous cache on failure and discard stale responses.
- Dependencies include Electron 45.5.0 and electron-builder 26.18.0. Desktop builds require a current Node.js installation; verification used Node.js 24.

## Verification

- `npm test`: 87 passing unit/service/Postgres tests.
- `npm run typecheck`: passing. Deno Edge Functions use a separate runtime and are excluded from the application TypeScript configuration.
- Browser coverage: 63 distinct passing cases using isolated services and representative records. Administration: overview, production, orders, merged invoices, sales, reports, profit calculator, catalogue and its subpages, agents, staff, activity log, presence, factory, safe, settings. Agent: catalogue, history, queue and finance. Shared: profile, notifications, public authentication/recovery pages, invoices and avatar crop.
- Window coverage includes employee and agent creation/edit forms, manual orders, invoice receipts, movement corrections, order status changes, catalogue creation, broadcasts, inventory, suppliers, factory finance, salary, rent, food, daily expenses, electricity, transport and customs. Desktop and mobile viewports were exercised.
- Production permission and accounting RPC checks ran inside a transaction that was rolled back. Protected financial records had identical fingerprints before and after those checks.
- Production ledger totals match agent balances. No unreversed orphan purchase entries or negative order/payment amounts were found in the final data check.
- Desktop and web version, HTML and bundle content are compared; updater metadata is checked against installer size and SHA-512.

## Boundaries

Browser fixtures never contact production or send mail/push notifications. Positive sign-in with a real password and delivery to real email addresses/devices require a separate controlled acceptance test. Destructive production actions were not used as UI tests.

The production dependency audit has no known vulnerabilities. Five moderate dependency notices remain in desktop build tooling. Supabase's existing leaked-password-protection warning remains an account configuration item; the connected tools do not expose an Auth configuration update operation. Internal RLS tables without client policies intentionally deny client access.

Database migrations use the versions recorded in production so a later migration push does not apply the same changes twice. No database backups, credentials, ZIP archives or private financial snapshots belong in the web deployment or GitHub release assets.
